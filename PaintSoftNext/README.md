# PaintSoft v2

WebGL2 + TypeScript による PaintSoft の作り直し版です。旧v1（`PaintSoft`）はリポジトリ履歴に残しつつ作業ツリーからは削除済みで、現行版はこのv2のみです。`.psft` はv1と共通形式なので、v1で書き出したファイルもそのまま読み込めます。

## なぜ作り直したか

v1 は「動くけれどスケールしない」状態でした。実測して分かった本当のボトルネックは、ファイル構成ではなく**描画アーキテクチャ**です。

| | v1 | v2 |
|---|---|---|
| スタンプ描画 | `ctx.fill()` を1スタンプずつ。ぼかし時は毎回 `createRadialGradient` を生成 | 全スタンプを1回のインスタンス描画。ブラシ断面はフラグメントシェーダーで解析的に評価 |
| 再描画 | `pointermove` のたびにキャンバス全体をクリアして全レイヤー再合成 | 入力は蓄積するだけ。GPU処理は `requestAnimationFrame` で1フレーム1回 |
| 再描画範囲 | 常に全画面 | ストロークが触れた矩形のみ（シザー矩形） |
| Undo | 全レイヤーの完全コピーを毎操作スタックに積む | 触れた矩形だけをGPUテクスチャとして保持 |
| コード | 単一の `app.js` 137KB・型なし | モジュール分割 + TypeScript strict（ビルド後 56KB / gzip 18KB） |

### 実測（RTX 4070 Ti / 2048×1536 キャンバス）

半径150px・ぼかし60 のスタンプを2000個描画したときの所要時間:

| 方式 | 所要時間 | 1スタンプあたり |
|---|---|---|
| v1のCPU方式（同一ロジックを再現して計測） | 695 ms（200個の実測値から換算） | 0.348 ms |
| v2のGPU方式（実測） | **4.4 ms** | **0.0022 ms** |

**約158倍**です。60fps の1フレーム予算16.7msで比較すると、v1は約48スタンプ、v2は約7,600スタンプ処理できる計算になります。しかもv1はこれに加えて `pointermove` ごとの全画面再合成が乗ります。

計測はアプリ内の「負荷テスト」ボタンからいつでも再現できます。

### 設計上の約束ごと

- **すべてのピクセルバッファは乗算済みアルファ（premultiplied）**。スタンプシェーダーは `vec4(color * a, a)` を出力し、合成は常に `(ONE, ONE_MINUS_SRC_ALPHA)`。レイヤー・ストローク・消しゴムが同じブレンド設定を共有できるのはこの統一のおかげです。
- **座標系はドキュメント原点が左上、Y下向き**。テクスチャのテクセル行0がドキュメントのY=0に対応し、Y反転は画面へ出す最後の1回だけ（`Compositor` の `uFlipY`）。
- **兄弟ノードの並びは下から上**。`rootIds` も各フォルダの `childIds` も合成順（下→上）で保持し、反転するのはレイヤー一覧の表示時だけです。v1の `.psft` も同じ並びなので、ファイル形式側で並びを気にする必要がありません。
- **エンジンはDOMを知らない**。`engine/` 以下はcanvas要素とGLコンテキスト以外のDOMに触れません。

### ストロークの流れ

1. `beginStroke` — ストロークバッファをクリアし、対象レイヤーをプレビュー用にコピー（1ストロークにつき1回だけの全面コピー）
2. `pointermove` — `getCoalescedEvents()` で取りこぼしなくサンプルを回収し、`StrokeBuilder` がスタンプ列に変換。**GPUには触れない**
3. 毎フレーム — 溜まったスタンプを1回のインスタンス描画でストロークバッファへ。プレビューは今フレームで触れた矩形だけ再構成
4. `endStroke` — ストロークバッファをレイヤーへ焼き込む。直前に触れた矩形だけをUndo用にスナップショット

「重ね塗り」がOFFのときストロークバッファは `MAX` ブレンドで塗り重なりを蓄積します。これにより、ゆっくり描いても速く描いても同じ濃さになります（手ブレ補正を強くするとスタンプ数が増えて勝手に濃くなる、というv1の挙動が起きません）。ONにすると従来どおり往復で濃くなります。

### 合成モードとフォルダ

「通常」以外の合成モードはハードウェアのブレンド機能では表現できないため、**背景をテクスチャとして読むシェーダー**で処理します。シェーダーは書き込み先を同時に読めないので、この場合だけ別バッファへ描いてから入れ替えます（ピンポン）。通常モードは従来どおり1回のブレンド描画で済むので、大多数のレイヤーに追加コストはかかりません。

対応モードは W3C の separable blend modes 12種（通常・乗算・スクリーン・オーバーレイ・比較（暗）・比較（明）・覆い焼き・焼き込み・ハードライト・ソフトライト・差の絶対値・除外）で、PSD書き出し時はそれぞれのPSDブレンドキーに変換します。

フォルダは、不透明度1かつ通常モードのときは中身を親へ直接描くだけで中間バッファを使いません。それ以外のときだけ subtree を専用ターゲットへ平坦化してから適用します。これが「フォルダ全体を一括で薄く（あるいは乗算に）する」と「中の各レイヤーを個別にそうする」の違いです。

### クリッピング

クリッピング指定のレイヤーは、直下の未指定レイヤーのアルファで抜かれます。連続した指定レイヤーは1つの土台を共有します（いわゆるクリッピンググループ）。合成は「土台を描く → 各メンバーを土台のアルファでマスクしつつ重ねる → 完成したグループを土台自身の不透明度と合成モードで下に重ねる」という順序です。土台を一度フル不透明で描いてからグループ全体に不透明度をかけるので、**半透明の土台にクリップしたレイヤーが二重に薄くなることはありません**。

### 選択範囲

選択範囲は8bitのカバレッジマスクとしてCPU側に持ち、変更時だけ単チャンネルテクスチャへ転送します。塗りつぶしはマスクを読む必要があり、反転・追加・削除は単なる配列操作なので、CPU側を正本にするほうが素直だからです。

描画の制約は**ストロークバッファをレイヤーへ焼き込む一箇所**でマスクを掛けることで実現しています。ブラシも消しゴムも同じ経路を通るため、ツールごとに選択範囲を意識する必要がありません。描画中のプレビューにも同じマスクを掛けるので、確定前後で見た目が変わりません。

- 長方形選択となげなわ選択（なげなわは4倍の縦サブサンプリングでアンチエイリアス）
- Shiftで追加、Altで削除。ドラッグ中は開始時のマスクから毎回作り直すため、行ったり来たりしても中間状態が溜まりません
- すべて選択 / 解除 / 反転、範囲の消去・塗りつぶし
- 境界表示はマスクからエッジを検出して描くので、どう作った選択でも正しく出ます。破線は画面座標基準なので、ズームしても見た目の間隔が変わりません

キャンバスの解像度を変えるとマスクは破棄されます（作られたサイズでしか意味を持たないため）。

### 変形

選択範囲（未選択なら描かれている範囲全体）のピクセルを**一度だけ**レイヤーから浮動バッファへ持ち上げ、そこから先の編集は行列だけで表現します。ドラッグ中は一切リサンプルしないので、縮小してから拡大し直しても劣化せず、操作コストは動かす面積に依存しません。実際に焼き込まれるのは確定時の1回だけです。

- ボックス内をドラッグで移動、角で拡大縮小、上の丸で回転
- 回転したボックスの角を掴んだときは、ポインタを現在の変換の逆行列で戻してから計算するので、画面の軸ではなく**ボックス自身の軸**に沿って伸びます
- `Enter` で確定、`Escape` で取消。他のツールに切り替えたときは確定します（取消にすると、うっかりキーを押しただけで作業が消えるため）
- ハンドルは書類座標から毎フレーム計算してSVGで描いています。CSSのtransformで箱ごと変形させるとハンドルまで拡大・回転してしまうため

キャンバスのリサイズ・プロジェクト読み込み・レイヤー削除の前には変形を取り消します（浮動バッファは古いサイズ・古いレイヤーに紐づいているため）。

### レイヤーマスク

マスクはレイヤーごとの任意のグレースケールバッファで、赤チャンネルが合成時にレイヤーのアルファを掛けます（白で表示、黒で非表示）。R8ではなくRGBAで持っているのは、**レイヤー本体とまったく同じストローク経路で塗れる**ようにするためです。ブラシ・筆圧・ぼかし・手ブレ補正がそのまま使えます。

マスクは合成の手前で一度スクラッチに焼き込みます。こうすると下流（合成モード・クリッピング・フォルダ）はただのテクスチャを見るだけで済み、マスクの存在を知る必要がありません。

- 「マスクを編集」中は、ブラシが**描画色の輝度**で塗り、消しゴムが白で塗ります。マスクは色ではなくカバレッジなので、消しゴムでアルファを削ると「隠す」と区別がつかなくなるためです
- Undo履歴はどちらのバッファを対象にしたかを保持するので、マスクへの操作を戻してもレイヤー本体は影響を受けません
- `.psft` にはグレースケールPNGとして保存され、PSDでは正規のレイヤーマスク（チャンネル -2 + マスク矩形ブロック）として書き出されます

### ノードエディタ

v1のノードビューを、同じレイヤーツリーの上に作り直したものです。v1から引き継いだ本質は「**位置が重なり順そのもの**」という点で、トップレベルのノードはY座標が上にあるほど手前になります。ボックスをドロップすると、その位置から重なり順を導出し直します。出力ノードへの配線は表示/非表示に対応します（v1で未接続のノードが合成対象外だったのと同じ意味）。フォルダの中身は、v1と同様にフォルダのボックス内の行として表示します。

レイヤー一覧とノードエディタは同じツリーの2つのビューで、どちらで並べ替えても他方へ反映されます。

## デスクトップ版（WPF + WebView2）

`Desktop/`（`PaintSoftNext.Desktop.csproj`）がデスクトップの殻です。v1のC#側（`.clip` の読み書き）をそのまま移植し、`<Content Include="..\dist\**\*.*">` のグロブでこのフォルダの `dist/` を読み込むようになっています（Viteの出力はファイル名にハッシュが付くため、個別指定ではなくグロブが必要です）。web側の窓口（`window.loadClipDocument` / `window.getClipExportDocument`）はv2でも実装済みです。

ビルド手順:

```bash
npm run build
dotnet publish Desktop/PaintSoftNext.Desktop.csproj -c Release -r win-x64 --self-contained true -o exe
```

`exe/PaintSoftNext.Desktop.exe` が生成されます。開発中に直接動かすだけなら `npm run build` の後に `dotnet run --project Desktop` でも起動できます。

## v1からの意図的な変更

- **ブラシサイズの基準**が既定でキャンバスのピクセルになりました（拡大すると太く見える＝一般的なイラストソフトの挙動）。v1と同じ「画面ピクセル基準」もグローバル設定から選べます。
- **重ね塗りが既定でOFF**（上記の理由）。
- **不透明度がセグメント内で補間される**ようになりました。v1は太さだけ補間し不透明度はセグメント単位で切り替わっていたため、筆圧変化が段状に見えることがありました。
- **1px以下のハードブラシでBresenham特例が不要に**なりました。v1はサンプルごとの整数丸めが原因で斜線に2px幅の瘤ができるため特例を持っていましたが、v2は座標を丸めないので現象自体が起きません。
- **レイヤーとフォルダに不透明度**が付きました（v1は常に不透明・通常合成）。
- **PSD書き出しがフォルダをグループとして保持**し、PackBitsで圧縮するようになりました（v1は展開＋非圧縮）。
- **選択とペン先を分離**しました。フォルダを選んでいる間もストロークは直前のレイヤーへ落ちます（一覧では ✏ で示します）。

### `.psft` の往復について

v1はノードを**出力ノードからの2D距離**で並べるため、ノードを右に動かすと重なり順まで変わります。v2はY座標のみで順序を決めるので、この2つが食い違わないよう、保存時の `x` は固定値にして距離をYに対して単調にしています。ユーザーが実際に置いた横位置は v1 が無視する拡張フィールド `editorX` に載せるので、v2同士では座標・順序・画素がすべて完全に往復します。

v1が書いた（横位置がばらばらな）ファイルを読むときは、**重なり順はv1のルールを優先**し、ボックスの位置はその順序に沿って整列し直します。順序と見た目が矛盾したエディタになるより、位置が動くほうが害が小さいためです。

不透明度と合成モードも拡張フィールドとして書き出します。v1は知らないフィールドを無視するので、v1で開けば従来どおり「不透明・通常合成」として表示されます。v1で出力に未接続だったレイヤーは、破棄せず非表示の最下部レイヤーとして読み込みます。

### 既知の制限

- 変形は自由変形（台形・メッシュ）には対応していません。アフィン変換のみです。
- マスクのサムネイル表示はありません（有無はプロパティ欄で確認できます）。
- 選択範囲は `.psft` に保存されません（作業中の状態として扱っています）。
- PSDのレイヤーは常にキャンバス全体の範囲で書き出します（使用範囲へのトリミングはしていません）。
- `.clip` の解析・生成はデスクトップ版のC#側が担当します。仕様が非公開のため、通常のラスターレイヤーのみが対象です。
